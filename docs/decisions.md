# Decisions

Choices made while building Mneme that the design brief left open or that differ from it.

## Toolchain and gate

- **Nightly 2026-10-28.** The newest dated nightly already installed on the build machine. Move the date in `mise.toml` deliberately.
- **Cargo's `unused_dependencies` lint, denied,** replaces rustc's `unused_crate_dependencies` from the house lint table. The rustc lint misfires on a crate with a library, a binary and integration tests.
- **Advisories fail on every vulnerability.** cargo-deny 0.20 has no severity threshold, so the brief's "High or Critical" became "any". `MISE_OFFLINE=1` checks against the local advisory database instead of fetching it.

## Index and history

- **gix stays at `sha1` and `blob-diff`.** Without gix's `parallel` feature a repository handle cannot cross threads, so each blocking task opens the repository from its path. Opening is cheap, and it means every read sees the newest objects.
- **A page id is 16 hexadecimal characters** of the SHA-256 of the creating commit and the first path.
- **Word counts are of the Markdown**, as in the wiki viewer, so `#` and link targets count as words.
- **A page over the markup budget** has its file name as its title, because finding its heading would need the parse the budget avoids.
- **A deletion is an event with `removed` set to the page's words.** It is not a version, so the windows, which count versions, leave it out.
- **Times are seconds since the Unix epoch.** `since` and `before` take the same. `since` keeps the events at its time and `before` leaves them out, so two windows that meet at one time never hold an event twice.
- **Commits in the API are full ids** of commits on `main`. A commit between two events of a page shows the text the earlier event left.

## API

- **Every listing has a `total`.** The page filters of search also work on `/v1/pages`.
- **Search scores are `-bm25`,** so higher is better and `desc` is the default order like every other numeric sort.
- **Snippets are lists of runs** `{ text, hit }` rather than marked-up strings, so the frontend never parses HTML out of page text.
- **Open questions are found when a version is indexed,** from the comrak parse that already gives the title and the search text, and stored in a table of their own. A question's `updated` is its page's `updated`, the last version, so a rename alone does not move it.
- **Each page carries its number of open questions.** It is a column the index writes with the questions, so `/v1/pages` and `/v1/pages/{id}` read it with no extra query.
- **A path finds the page whose last event at that path is newest,** among pages that are not deleted. Two pages never hold one path at the same time, so that page is the one that had it most recently. A live page at the path is always that page. Deleted pages are left out before choosing, so a page that moved away is found even when a later page at the path was deleted.
- **docs/api.md links its examples** in `tests/fixtures/api/` instead of copying them, so the documented responses are the tested ones.

## Reading a folder

- **`mneme serve --folder DIR` is the reading API of a clone on the same machine,** with the same index and the same `/v1` routes, read from `refs/heads/main` in `DIR/.git`. `--folder` conflicts with `--repo` and `--tokens`. There are no Git routes, no hook, no tokens and no machine state, so `/v1/machines` is empty, and it never runs `git`, so it skips the version check. A test runs it with an empty `PATH` and compares every file under the folder, `.git` included, before and after.
- **Loopback only, since the reading API has no login.** The address must be a loopback one, an IPv4-mapped one included, and is `127.0.0.1:8081` by default. Every request must name `localhost`, `127.0.0.1` or `[::1]`, with any port, in `Host`, and in the request target when that is absolute. Any other name, or none, is `421` with `{ "error" }`, `/healthz` included. That keeps a web page that points a name of its own at `127.0.0.1` from reading the wiki through the browser.
- **The index follows `main` by reading its tip every 2 seconds.** One ref is cheap to read, and a file watcher would have to follow packed refs and lock files. New commits are added as after a push. A tip that does not descend from the indexed head along first parents, as after a hand reset, has the index built again from scratch outside the lock and swapped in, so reads go on meanwhile. A failure is logged once until it changes, and the old index keeps answering.
- **`--exit-with-parent`,** hidden from help, records the parent's process id at start and checks it every second. When it changes, the server stops as on SIGTERM, so a child of Atrium never outlives it, even after a SIGKILL.
- **`mneme serve --repo` now listens on `127.0.0.1:8080` by default,** where it was `0.0.0.0:8080`, so a server started by hand is not on the network until told to be. The image passes `--addr 0.0.0.0:8080` and is unchanged.

## Git over HTTPS

- **The tokens file is one JSON object** of machine name to hexadecimal SHA-256.
- **A 401 carries `WWW-Authenticate: Bearer`** and no body. HTTP asks for the header, and it says nothing about why.
- **Only the three smart HTTP routes exist.** The dumb protocol is not served.
- **A body over 64 MiB** is refused with 413 when its length is declared, and cut off when it is streamed.
- **The push check also refuses a deletion of `main`,** before `receive.denyDeletes` would, and compares `.git` without case, since clones on macOS and Windows read `.GIT` as `.git`.
- **Git checks every pushed object** (`receive.fsckObjects`). It refuses tree entries named `.` or `..`, and every name that HFS+ or NTFS reads as `.git` (`.GIT`, `git~1`), before the push check runs. The push check's own `.git` comparison stays as a second line.

## Image

- **The runtime is Alpine 3.22's Git, copied into `scratch`.** The server runs `git http-backend`, which no small image ships. Chainguard's Git image (2.56) and `alpine/git` (2.54) leave it out, and `buildpack-deps:trixie-scm` has it but is 376 MB, runs as root and has 153 High or Critical findings. Alpine puts `git-http-backend` in the `git-daemon` package (`apk info -L git-daemon` lists it beside `git-daemon` and `git-shell`), not in `git`. The `Containerfile` installs `alpine-release`, `busybox`, `git` and `git-daemon` with `apk add --root` into an empty root and copies that into `scratch`, so the image has `/bin/sh` for the push check's hook and no package manager, while `/lib/apk/db/installed` stays for scanners. It is one `RUN` more than a plain `apk add` in the final stage.
- **The base is pinned by digest, the packages are not.** `alpine:3.22` and `rust:1.99.1-alpine` are pinned by their index digests, and the base's signing keys check every package. The packages come from Alpine's 3.22 repositories at build time, at whatever version the branch has then, so two builds of one commit can differ: a rebuild picks up Alpine's security fixes to Git, curl and busybox without a change here, and can also pick up a Git release Alpine moved the branch to. `mise run image` starts the server, which refuses a Git older than 2.45, and scans every build, so a rebuild that breaks either fails. Pinning `git=2.49.1-r0` would make a rebuild fail as soon as Alpine replaces that release, which it does for every security fix.
- **The binary is built with stable Rust 1.99.1, not the gate's nightly,** because a nightly would need `static.rust-lang.org` during the build. It is linked with `+crt-static` for the explicit target `x86_64-unknown-linux-musl`. Without `--target` the flag also reaches the proc macros, which musl cannot build as shared objects. `mise run image` checks that the binary names no program interpreter.
- **Trivy sees the Alpine packages only.** The binary carries no dependency list for it to read, so the Rust dependencies stay with `cargo deny` in the gate. Trivy is pinned to 0.76.2 in `mise.toml`, and its lock entry has the release's URL and checksum for `linux-x64`. It once had neither, having been written offline, and CI's install then failed with `No lockfile URL found`.
- **`mise run image` checks the container as it will run**: UID 65532, a read-only root, the repository on a named volume at `/data`, the tokens file mounted read-only, no `apk`, a real clone and push, a refused symlink push that shows the hook ran, a fresh clone and the page on `/v1/pages`. It then runs the autosave service from the image against that server, so that the service's Git options are run on the image's Git as well as on the host's: `mneme autosave init` into two empty folders, one save that the other folder fast-forwards to, and one edit of the same line in both that the second replays with an `Overlap` trailer. Each runs in a container of its own on the host's network, as UID 65532 with its folder mapped to the user who runs the check, and is stopped with SIGTERM once it reports what was asked; a `blocked`, `stopped` or `offline` tick fails the check. The image needed nothing added for this. It then fails on any High or Critical finding. The first push against Git 2.49.1 found that the push check needed Git 2.50, which is fixed.
- **The push check's reading of Git is tested on bytes from both Gits.** `scripts/git-output.sh` makes one repository with a merge, a symlink, an executable, a submodule and paths with a space, an umlaut, a tab and a newline, and saves what `rev-list --parents` and `ls-tree -r -t -z -l` print for it, from the host's Git and from the image's, in `tests/fixtures/git/<version>/`. The unit tests in `src/hook.rs` parse both. Run it again when the image's Git moves.

## Machine status

- **A report is a header on a Git request,** `Mneme-Report` with the JSON in base64, sent with `git ls-remote` when it is due. It used to be a `POST /git/status` from a second HTTP client in the service, `ureq` with its own TLS stack and certificates, which was never tested against TLS here and could disagree with Git about the server. Now Git sends it with the system's certificates and any proxy Git is set up to use, exactly as it syncs. The route and `ureq` are gone, and with them `rustls`, `ring` and `webpki-roots`. The release binary went from 15,327,408 to 12,588,536 bytes.
- **The report gets a request of its own** instead of riding on a fetch or a push. The tick's outcome is known only at its end, after both, so a fetch could only carry the tick before. `ls-remote` with the server's URL needs no repository, so a service that the folder guard stops before any fetch still reports. It speaks protocol version 0, which lists the refs in one request where version 2 takes two, each a `git http-backend` on the server: 48 seeds of the simulation took 29.7 to 31.4 s that way and 37.0 to 39.5 s with version 2, against about 25 s with the old `POST`.
- **`seen` counts Git requests that carry no report,** the fetches and pushes. A report leaves it alone, so a service that still reports but no longer syncs shows its last sync.
- **A machine also has `reported`,** the time its last report arrived, which the brief did not list. A blocked service makes no fetch, so without it a blocked service that still reports would look like a stopped one.
- **Machine state is one JSON file, `mneme/machines.json` inside the bare repository,** so it lives on the data volume beside the history it describes and needs no option of its own. Git reads only its own files in a repository's directory, so the file is in no ref and no object, and neither a clone nor a fetch sees it. One task writes it, every 3 seconds when something changed and once more after the server stops taking requests, through `machines.json.tmp` and a rename, so a crash leaves the old file or the new one. At start a missing or unreadable file is one `machines` log line with the error and an empty state, never a failed start. Machines no longer in the tokens file are dropped from it.
- **`behind_since` is when the heads first differed, either way round,** and the server's time, not an author time. A push that moves the server's head sets it for every machine whose reported head is now another, and so does a report of a head that is not the server's, such as a commit not yet pushed. A later report of another wrong head keeps the first time. Whenever the two heads are the same it is `null`, so a push that makes the server's head the one a machine reported clears it too, before that machine reports again; the brief named only a matching report, but then `current` could be `true` beside a time. The server compares at start as well, so a head that moved while it was down counts from the start. The server's head is kept beside the records under one lock, so a report and a push cannot each compare against the other's stale head.
- **A report is checked at the door.** `state` is 1 to 64 bytes, `detail` at most 1 KiB, `head` a full lowercase commit id or `null`, and no other field. A header over 4 KiB is `413`, one that is not base64 or not JSON `400`, and a report of the wrong shape or with a bad value `422`. The Git request is then not run, so `ls-remote` fails and the service sends the report again on the next tick.

## Autosave

- **Local commits are replayed with `git merge-tree` and `git commit-tree`, not `git rebase`.** This departs from the brief, and the reviewer accepted it on this evidence. A rebase walks the work tree through every step and stops on a conflict with markers in the page, so a writer can read or edit a half-rebased folder. Its recovery after a kill, `git rebase --abort`, resets tracked files and throws away an edit made while it was stopped. With Git 2.56: commit `one/two/three` to `p.md` and `other` to `q.md`; on a branch `up` change line two to `UP`; on `main` change it to `LOCAL`; `git rebase up` stops with `UU p.md`; write `agent edit while stopped` to `q.md`; `git rebase --abort` succeeds, and `q.md` reads `other` again. The edit is gone without a word. The replay writes only objects. The folder moves once, with Git's two-way merge, which refuses rather than overwrite an unsaved edit or an untracked file, and `main` moves after it only if it is still the commit the replay started from (see [A commit that lands as the folder moves](#a-commit-that-lands-as-the-folder-moves)). So there is no rebase state, no marker file and nothing to abort, and every tick derives its work from the repository as it finds it.
- **Where a path overlaps, the replayed commit's entry wins**: Git's stage 3 for that path, or no file when that commit has none. A local edit stays, a local delete stays a delete, and a local rename wins. The commit gains `Overlap: <commit>`, the newest commit on the other side that changed one of the overlapping paths, which is the edit that lost. A commit whose replay changes nothing is left out.
- **Git runs without the user's global and system config**, with `core.excludesFile` and `core.attributesFile` at `/dev/null`, no credential helper, no signing, no prompt and none of the caller's `GIT_*` variables. A global gitignore would otherwise keep new pages such as `AGENTS.md` from ever being saved, and a signing key or credential helper can wait for a person. Ignores belong in the wiki's own `.gitignore`. The token is given as `http.<server>.extraHeader` through `GIT_CONFIG_*`, so Git sends it only to the server.
- **The mass-delete stop counts pages lost**: deleted pages less new pages, before anything is staged. Moving every page into a folder loses none. A wiped folder loses all of them. Nothing is committed or staged while it holds, and fetch and push go on so earlier saves still reach the server.
- **A fetch happens when the head moved since the last one**, which covers "right after a save" and hand commits, **after a push found the server had moved**, and otherwise once per interval. Integration runs only after such a fetch, so a replay is never built on a stale view of the server.
- **The service stores file stats in the index itself.** Its `git status` runs without optional locks, so that it never takes the index's lock from under a writer, which also means it never stores what it learns. `git read-tree -m -u`, like `git merge --ff-only` and `git reset --keep`, refuses to move a file whose index entry is out of date even when its text is unchanged, so it runs after `git update-index -q --refresh`, which writes only the index. The simulation found this when an index rebuilt from `HEAD`, which holds no stats, met a replay on the same tick. The service also refreshes once the head has held for a whole tick. A clone or checkout writes pages and the index in the same second, Git then reads those pages again on every status, and on a 5,000-page folder that cost 30 ms of CPU a tick instead of 4.6.
- **Polling costs 0.18 % of one core when idle on a 5,000-page folder**, the median of five two-minute windows (0.175 % to 0.208 %), with the release build, the default timings and systemd's default `PATH`. That is the service's own CPU and every Git command it waited for, from `/proc/<pid>/stat`; the service itself is at most 0.02 s of each window. A `git status` costs 4.8 ms and a fetch with nothing new 9 ms, which predicts 0.13 %, and the rest is in the same Git commands. Before the index was refreshed it was 0.63 %. File events are not needed for now.
- **The service needs Git 2.45.0 or newer,** and `run` and `init` refuse to start with an older one, before they change anything, and say which version they found. The replay is the newest need. `git merge-tree --write-tree` came in 2.38.0 and its `--merge-base` in 2.40.0, and since 2.45.0 the three trees of the merge "only need to be trees, not necessarily commits", in the words of its release notes. The replay passes the empty tree as the base of a commit with no parent and as its own side when the server has no `main`. The rest is older: `GIT_CONFIG_COUNT` came in 2.31, `GIT_CONFIG_GLOBAL` in 2.32 and `fetch --no-write-fetch-head` in 2.29. These were read from the release notes of Git 2.52's documentation, and the tests run 2.56.0. The server's newest need is `init --initial-branch`, since 2.28, and the rest of what it runs (`http-backend`, `receive.fsckObjects`, `rev-list --parents` and `ls-tree -l`) is older. The push check used to read `git rev-list -z`, whose records end in NUL only since 2.50 ("git rev-list" learns machine-parsable output format that delimits each field with NUL, in 2.50.0's release notes); with Git 2.49.1 in the image it read each commit id with a newline on its end and refused every push. It also read each tree with `ls-tree -z --format=...%(path)`, and `%(path)` quotes a path that holds a tab, a newline or a byte over 0x7f even under `-z`, in 2.49.1 and in 2.56.0 alike, so `minnen/café.md` reached the rules as `"minnen/caf\303\251.md"`, which does not end in `.md`, and a page of any size up to 10 MiB with such a name was stored. It reads `ls-tree -z -l` now, which gives each path as it is. It reads one commit per line now, which every version prints the same way, so `mneme serve` checks for the same 2.45.0 at its start, before it reads the tokens or touches the repository.
- **One folder takes one service.** `mneme autosave run` holds an exclusive advisory lock on `.git/mneme-autosave.lock` for as long as it runs, and a second service on the same folder exits at once and says so. Two would each commit and move the folder under the other. The lock goes with the process, so a killed service leaves nothing behind to clean up, and the file itself is never removed, since a new service could otherwise lock a new file while an old one still holds the removed one. `run` therefore needs `.git` when it starts: on a folder that is not a clone it exits and says to run `init`, where it used to tick as `blocked`. A `.git` that goes away while it runs is still the guard's `blocked`.
- **Every failure is an outcome.** A fetch or push that cannot reach the server, or that the server answers with 401, is `offline` with Git's message. An unexpected Git failure is `blocked` with Git's message and is tried again on the next tick. The service exits only on SIGTERM or Ctrl-C.
- **Whether a refused push lost a race is read from the server, not from Git's words.** After any refused push the service asks for the server's `main` (`git ls-remote`). When it is no longer what the fetch saw, the push lost a race and the next tick fetches and replays. Git words two such races differently: `[rejected] (fetch first)` when it notices before sending, and `[remote rejected] (failed to update ref)` when the server only notices as it takes the ref's lock, which reads like a hook's refusal. Two services saving the same page at once hit the second, which a test now makes on purpose. When the server's `main` has not moved, the push check or Git's own object check refused it, and the push is `blocked` with the server's message and not tried again until the head changes.
- **Autosave commits are by `<machine> <autosave@machine>`**, dated by the tick's clock. Replayed commits keep their author, author time and message; their committer is the machine.
- **Machine status reports carry the tick's outcome** as the state, its reason as the detail, and the folder's head, or `null` when a guard stopped the tick before reading it.
- **The quiet time is measured by modification time against the tick's clock.** A deleted file counts as quiet. A file dated in the future waits until the clock passes it.
- **The kill test kills the service's process alone**, as `kill -9` or a crash would. Git commands it started run on to their end. No tick may be `stopped`, and none may be `blocked` except on an `index.lock` under ten seconds old, which is such a command still running: on a loaded machine the service that replaces a killed one can tick before that command ends (seen once, at a load of 46 on 8 cores). The service must not end blocked. An earlier version allowed one `blocked` tick, read as the restarted service meeting such a command's ref update; it was the push race above, and with that fixed, ten seeds and about 270 kills show none. The unit uses `KillMode=mixed`, so a stop sends SIGTERM to the service alone and it finishes its tick.

### A commit that lands as the folder moves

The service used to check that `HEAD` was still the head it replayed from and then run `git reset --keep <tip>`. A hand commit that landed in between was moved off `main` by the reset, and its change left the folder: `reset --keep` read the new `HEAD`, saw the hand commit's files as clean, and set them to the tip's text. The commit survived only in the reflog. A test that commits by hand right before `reset` showed it, and the same race before `merge --ff-only` made a tick `blocked`, since the merge then found local history ahead.

- **The folder moves first, then `main`, and `main` only if it has not moved.** `git read-tree -m -u <head> <tip>` is the two-way merge `reset --keep` runs, but from the head the replay was built on rather than whatever `HEAD` is by then. It keeps every edit and staged change and refuses rather than overwrite one. `git update-ref refs/heads/main <tip> <head>` then moves `main` only if it is still `head`, under the ref's lock.
- **So no commit is moved off `main`.** `git commit` moves `HEAD` the same way, only if it is still the parent it read. Of a hand commit and the move, one moves `main` and the other fails. When the hand commit wins, the service's `update-ref` fails, and the commits that landed, those on the new `main` that are neither below the old head nor on the server, are replayed onto the tip with the same replay. The folder then moves from the tip to that replay, which changes nothing in it, and the swap is tried again. When the move wins, the hand commit fails with `cannot lock ref 'HEAD'` in the agent's terminal, and its changes stay staged in the folder, so the next save takes them. After four rounds of commits landing, the tick is `blocked` and names the last one, and the next tick starts over from it. Nothing is dropped in any round, since `main` only ever moves forward from what it holds.
- **The two orders a hand commit can land in.** Before the folder moves, the hand commit's files differ from the old head, so the merge keeps them, or refuses when the server changed the same file, and nothing moves. After the folder moves and before `main` does, the hand commit is made from the moved index, the tip's files and the agent's. Replaying it from the old head onto the tip changes only the agent's files. A test races a hand commit to each point, for a replay and for a plain fast-forward, and the simulation does so at random on one clone per seed.
- **The window this leaves: the folder has moved and `main` has not.** It lasts from one Git command to the next. A hand commit in it is the second order above. A service killed in it with SIGKILL, since the Git commands it started run on, leaves the server's changes in the folder as staged changes. The next tick saves them, the replay finds them on the server and leaves that commit out, and nothing is lost; a test makes that state by hand. The one way it could cost more is the mass-delete stop: when the server's changes delete most pages, that save stops and waits for a person. `reset --keep` had the same window inside one command, between writing the index and moving the ref, which a power cut can open as well.
- **A `git` program in the service's configuration** is the hook point the tests race through: a shell script that runs a hand commit right before a named Git command, then the command. The service runs `git` from `PATH`.

### Files the server would refuse

- **One set of rules, in `rules`, for the push check and the save.** No symlink, no submodule or nested repository, no path part named `.git` in any case, no page over 1 MiB, and no file of any kind over 10 MiB. The last is new on both sides.
- **A save stages only the changed paths that keep the rules,** with `git update-index --add --remove`, and leaves the rest in the folder. Before, it ran `git add --all` and pushed what came of it: the server refused the commit, and every later commit had the bad one below it, so the clone was blocked until a person rewrote history. A folder with a `.GIT` in it was blocked sooner, since `git add --all` fails on it.
- **What is staged is checked again, not only what the folder looked like.** A file can turn into a symlink or grow between the look and the staging, and a person can stage one by hand. Each staged entry that breaks a rule goes back to what `HEAD` has, so the file stays in the folder and out of the commit.
- **A new file Git will not stage is left out too.** Git refuses some names that only Windows or macOS read as `.git`, such as `git~1`, and `update-index` skips them without failing. Such a file stays a change in every `git status`, so the service lists it with the reason `a name Git will not store` and does not wait for it.
- **A left-out file is not an unsaved edit.** Only changes that keep the rules count for the quiet time and hold back the replay. A tracked page that turns bad keeps its last good version in history.
- **A left-out file the server changed blocks the folder, and says so.** When the server changes such a page, or adds a page where the folder has a left-out file, Git's two-way merge refuses to overwrite it, and no save will ever take it, so the folder can never move on its own. The service used to wait there as for an edit in the way and report `idle`. Now, when the move fails, it compares the paths the move would change (`git diff-tree`) with the files it leaves out, and when one is among them the tick is `blocked` with each such path and its reason. Ticks that do not fetch say the same while the head has not moved and a named file is still left out, so the state does not flicker between fetches. Fixing the file is an edit like any other: it is saved, replayed over the server's change with an `Overlap` trailer, and pushed.
- **A hand commit that holds a bad file is still pushed and refused,** and the outcome is `blocked` with the server's reason. It is a person's commit, and a person fixes it.
- **The report lists what is left out,** up to 20 paths and as many as fit in its header, and counts the rest. The simulation drops each kind of bad file, at a new path, and sometimes fixes one. Every bad file must end as a skipped path in the server's report, never as a blocked tick. The server never changes those paths, so the blocked case above stays out of the simulation and keeps its rule of no blocked tick. A test of its own covers it.

### The simulation's oracle

The simulation records every commit a clone makes, from the `commit` entries in the reflog of its `main`, which are both the service's saves and hand commits, and leaves out merges, which the server cannot hold. A commit's key is its author name, author time and subject. At the end, after every clone has gone online and ticked until nothing changed, the commits on the server's `main` after the starting commit must meet all of this:

1. No key appears twice, and every key belongs to a recorded commit.
2. Every recorded commit's key appears exactly once, with the same author email and a message that starts with the recorded message. The one exception is a commit whose every change deletes a page that the server's history also deletes: replaying it found nothing left to do.
3. No commit is empty.
4. For each recorded commit `C` found as `S`, Git's three-way merge of `C` onto `S`'s parent, with `C`'s parent as the base (`git merge-tree --merge-base=C^ S^ C`), decides the rest. When it is clean, `S` is exactly that merge and has no new `Overlap` trailer. When it conflicts, `S` has one new `Overlap` trailer and every conflicted path in `S` holds `C`'s entry, or no file where `C` has none.

Every edit the simulation writes carries a token used once, and every page it creates or renames gets a new path, so a change other than a deletion can never already be on `main`. That is why "unless its change was already there" can be checked as deletions only. Each commit is replayed at most once in the simulation, because ticks run one at a time and a replay always follows a fetch in the same tick, so `S`'s parent is the commit it was replayed onto.

Five kinds of overlap are also made on purpose, on a page both clones hold as the server has it: the same line changed, the same new page created, an edit against a delete either way round, and one page renamed two ways. Both clones save before either syncs, and the simulation checks at once that the second clone's tick pushes and that the server's head has one `Overlap` trailer and that clone's side: its text, its delete, or its name.

The gate runs 128 seeds of 80 steps against the server, about a minute and a half here, and the same against a bare repository, under a minute. `mise run soak` runs 2000 seeds of each and the kill test over 20 seeds.

### A stale `index.lock`

A Git command killed with SIGKILL, by a power cut or by killing the whole unit, leaves `.git/index.lock` behind, and every later command that needs the index fails with `File exists`. Reproduced with Git 2.56: SIGKILL a `git update-index --index-info` that holds the lock while it waits for input, and the next `git add` fails.

- **A lock is stale when its modification time is more than `--stale-lock` seconds old by the tick's clock, 300 by default.** The service then removes it, logs `stale lock removed` with its age, and carries on in the same tick. Until then the tick is `blocked` with the lock's age in the reason. No process is consulted. A command that is still writing the index keeps the lock's modification time fresh, and with Git 2.56 neither `git commit` with its editor open nor `git add -p` waiting for an answer holds `index.lock` at all, so a lock that sits unchanged for minutes belongs to a command that died. With pages capped at 1 MiB by the push check, no honest command in a wiki folder writes the index for that long.
- **A check of `/proc` was tried and dropped.** The rule first asked for no live `git` process to own the lock, judged from `/proc`. Inside the hardened user unit the check is blind: a systemd user unit with any option that needs a mount namespace (`ProtectSystem`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ProtectKernelTunables`) runs in a user namespace of its own (`uid_map` is `1001 1001 1`), and from there `/proc/<pid>/cwd` and `/proc/<pid>/exe` of the user's other processes cannot be read, though `comm` and `cmdline` can. The sandbox was kept and the check dropped.
- **An index the dead command left unreadable is read again from `HEAD`.** After removing a stale lock the service checks that `git status` works. When it does not, it runs `git read-tree HEAD`, which writes only the index, so every edit in the folder stays and shows as a change to save. When that fails too, the tick is `blocked` with Git's message.
- **The one remaining risk:** a command that holds the lock for more than five minutes without writing to it loses its index update, and its work tree is untouched.

The simulation leaves such a lock, half the time with half an index, and the kill test leaves one while a service is down. Both require that no tick is ever blocked.

### Any Git remote

- **`--remote URL` is the other choice to `--server URL`, and `run` and `init` take exactly one.** `origin` is the URL as given, except that a local path is made absolute, since Git runs in the folder. `--remote` takes an `https://` URL, an `http://` URL to `localhost`, `127.0.0.1` or `[::1]`, a `file://` URL or a path, and nothing else. The URL is read by Git's own rules, `scheme://`, a remote helper's `name::`, then a colon before any slash for SSH's short form `user@host:path`, and a path otherwise, so that SSH in any form, `git://`, `ext::` and every other remote helper are refused before anything changes, with one message that names what Mneme syncs with: a Mneme server with `--server`, a Git host over HTTPS with `--token-file`, or a path. One table-driven unit test covers the refusal.
- **SSH was dropped,** with `--ssh-key`, the host-key handling and `core.sshCommand`, to keep one login per kind of remote: a server's token, a Git host's token over HTTPS, and none for a path. A Git host's token over HTTPS, such as a fine-grained token scoped to the one repository with write access to its contents, covers what a deploy key did. SSH also brought the user's ssh configuration, agent and host keys into a service that must never wait for a person, and a home folder that the unit keeps read-only, so `init` had to learn a host's key before the service could use it.
- **An HTTPS token is HTTP Basic authentication:** `Authorization: Basic base64(user:token)`, with the URL's user name, percent-decoded, or `git` when it has none, as `http.<url>.extraHeader` through `GIT_CONFIG_*` like the server's token. Git sends it only to that URL, it is in no file, no argument and no log, and a wrong token fails at once since Git may not prompt. Git hosts take a token as the password, and some want the user name the token belongs to, which the URL then carries. A URL that holds a password is refused, since it would be in `origin`, the unit and the log. Plain `http://` is refused unless the host is `localhost`, `127.0.0.1` or `[::1]`, since the token and the wiki would cross the network in clear text. `--server` keeps taking an `http://` URL, as it always has.
- **A login that does not fit the remote is refused before anything changes:** a token for anything but HTTPS.
- **A remote that is not a server takes no report.** The service logs a `skipped` line instead whenever the files it leaves out change, since there is no `/v1/machines` to list them. Everything else is the server's code path: save, fetch, replay, overlap, push, refusals and offline handling. A plain remote has no push check. The service's saves never stage a file the rules refuse, but a person's hand commit that holds one is pushed, where a server would refuse it.
- **The folder is made absolute for `--remote` and left as given for `--server`,** which keeps the server's path exactly as it was. A relative folder other than `.` cannot work there: Git runs in the folder with `GIT_DIR` relative to the start.
- **The simulation runs against a bare repository too,** with the same seeds and the same oracle, and checks every commit on the remote against the rules instead of the reports. HTTPS is tested against `git http-backend` behind a small test server that refuses any other `Authorization`.

## `mneme init`

- **One unit, written from `src/mneme-autosave.service`,** which the binary carries, so the unit always fits the binary that writes it. It replaces `deploy/mneme-autosave.service`: `deploy/` is the Kustomize base, and the image's build copies only `src`. The template keeps that unit's hardening, restart policy and `KillMode=mixed`, and its header says that `mneme init` wrote it.
- **Every path in the unit is absolute:** the binary, from `current_exe`, the folder, the token file, and a remote that is a path. The folder and such a remote are the unit's `ReadWritePaths`, since a push writes the remote. The name is written as given or as found, where the old unit had `%l`, so the unit says what it runs.
- **Quoting.** A word of `ExecStart` is double-quoted when it needs to be, with `\` and `"` escaped and `%` and `$` doubled, since systemd reads specifiers and variables inside quotes too. `ReadWritePaths` unquotes but keeps escapes, so a folder whose path holds a quote, a backslash or a control character is refused. `systemd-analyze verify` accepts a unit for a folder with a space in its path, a remote with `%` in its name and a name with `$`. A printed command is quoted for a POSIX shell.
- **A different unit is refused without `--force`,** before the folder is touched, and the refusal names the file. The same unit is left as it is, so `mneme init` can run again. After `daemon-reload` and `enable --now`, a unit that replaced a different one is also `try-restart`ed, which the brief did not ask for: `enable --now` leaves a running service on its old command.
- **`--no-service`, or no executable `systemctl` on `PATH`, installs nothing** and prints the `mneme autosave run` command.
- **`mneme init` is for a person, so it prints sentences and no log lines.** Making the folder ready returns what it did, a clone, a clone that was there already or a folder of files taken as the wiki, and `mneme init` says that in a sentence, where it used to also write `mneme autosave init`'s JSON `initialized` line to standard error. `mneme autosave init` and the service still log JSON lines, for systemd's journal and for scripts. A failure is still the one JSON `failed` line every command ends with.
- **A folder of files that is not a repository** becomes one when the remote has no `main`: `git init --initial-branch=main` without `GIT_DIR` and `GIT_WORK_TREE`, so that Git records no `core.worktree`, and `origin`. Nothing is committed then. The service's first save commits the files and pushes them, with the rules and the mass-delete stop like any save. When the remote has a `main` it is refused, and says to move the files out, clone with `mneme init` and move them back. A `.git` that is a file, as in a linked worktree, is refused as before. Only `mneme init` takes such a folder: `mneme autosave init` refuses it as it did, so the `--server` path behaves as before.
- **`--name` defaults to the host name up to its first dot,** from `/proc/sys/kernel/hostname`, as systemd's `%l` has it, and `--folder` to `~/wiki`. `$XDG_CONFIG_HOME` counts only when it is an absolute path, as the XDG base directory rules say.
- **The sandbox was tried once for a plain remote:** a transient `systemd-run --user` with the template's properties adopted a folder of files, saved them and pushed them to a bare repository on the same machine. The tests use a temporary `XDG_CONFIG_HOME` and a `systemctl` on `PATH` that records its arguments.

## The installer

- **`install.sh` installs both apps unless named, from each one's latest release,** and finds the tag by following `releases/latest` to the tag's page, since the signing identity names the tag. Every app is downloaded and checked before any is installed, so a bad checksum or signature leaves the folder as it was. A binary goes into place as a copy in the install folder and a rename, which replaces it in one step even while a service runs the old one. When it replaced one, it says that a running service goes on with the old version until it restarts, and how to restart both units, since Atrium runs `mneme serve` too.
- **Everything is in functions, and the last line calls `main`,** so a download cut short by a dropped connection fails to parse and runs nothing. `curl` takes only `https` for the downloads and their redirects.
- **One override, `MNEME_RELEASES_URL`, replaces `https://github.com/notes-supply`.** Atrium's unit comes from `atrium/raw/<tag>/contrib/atrium.service` below it, which GitHub redirects to the raw file, so a test serves the whole release from one folder. The identity cosign checks never comes from the override.
- **Atrium's unit is installed only beside binaries in `~/.local/bin`**, since it runs `%h/.local/bin/atrium` and `%h/.local/bin/mneme`, only where `systemctl` is on `PATH`, and never over a file already there; it is downloaded only then, so an install elsewhere never depends on it. It is loaded with `daemon-reload` when `systemctl --user show-environment` answers, and otherwise, as over SSH or on a headless machine, installed anyway with a note to reload before enabling it. It is never enabled, so nothing starts without being asked. When Atrium is installed without a `mneme` beside it, the next step is to install Mneme rather than to start Atrium.
- **The test pipes the script to `sh -s --`** as the README does, with a `PATH` of only the tools it may use, symlinked from `/usr/bin`, and a `uname`, `git`, `systemctl` and `cosign` of its own, against a release served on loopback. It also checks that the temporary folder is empty afterwards. By hand the script was also run against the real v0.1.0 releases, with cosign, and under busybox `sh` without it.

## Screenshots

- **The images in `docs/images` come from a real run, `mise run screenshots`.** Two containers of the server's image are the machines, with the host names `laptop` and `desktop`, so `mneme init` names them as it would, and a third is the server. Their `systemctl` is a stand-in that runs the unit's `ExecStart` when `mneme init` enables it, since a container has no user manager and the script must not reach this computer's. The terminal image is the tty's own output, colours included, with `GIT_PAGER=cat` so that `git log` prints as with GNU less and Git's `LESS=FRX`; the one line that is not output says how long the script waited. The overlap comes from taking the desktop off the network, changing one line on both, and connecting it again.
- **Atrium is the v0.1.0 release binary,** checked against its `SHA256SUMS` in a temporary folder, with `TZ=UTC` and a browser in UTC so that its clock and its rows agree. Playwright comes from a checkout that has it, and `MNEME_CHROMIUM` lets it run the system's Chromium when Playwright's own build is missing. oxipng compresses the images without loss, to between 60 and 130 KB.

## Deployment

- **Flux verifies cosign's classic `.sig` signature, so the release signs in that format.** Flux 2.8.2 found no signature in cosign 3.1.4's default bundle format, which a registry without the referrers API, GHCR among them, stores under a `sha256-<digest>` tag, and it verified the same artifact signed with `--new-bundle-format=false`. Shown on kind with a key; keyless signing is proven only once `release.yml` has run on GitHub.
- **The Services live in the cluster repository.** A release that may write a Service can claim an external IP on every node or ask the Tailscale operator for a new tailnet host, which changes the network beyond the namespace. The deployer may write only Deployments, StatefulSets, ConfigMaps and PodDisruptionBudgets, and read ReplicaSets and pods, which Flux's health check needs.
- **`release.yml` is a reusable workflow that CI calls after the gate.** The keyless identity the cluster verifies is that one file on `refs/heads/main`. The `image` job builds and checks the image with no publishing rights, and the release job pushes that exact archive.
- **A rerun of an older run publishes nothing.** The release job stops unless its commit is still `main`'s head, so only the newest commit can move the `main` tag. Runs on `main` are already serialised by the workflow's concurrency group, and the release job has its own.
- **A Deployment with `Recreate`, not a StatefulSet.** The volume claim belongs to the cluster repository, which a release may not change, and a StatefulSet would make its own claims. One pod writes the repository, so the old pod stops before the new one starts, and a release whose pod never gets ready leaves Mneme down until a revert.
- **No disruption budget.** With one pod, a budget that keeps it would block every node drain.

## Release binaries

- **A tag `v*` on a commit on `main` publishes binaries,** from `.github/workflows/binaries.yml`. Its first job asks GitHub to compare `main` with the tag's commit and stops unless the commit is on `main` (`identical` or `behind`), so a tag on a branch publishes nothing. It needs only `contents: read`.
- **Each binary is the image's.** The build job runs `podman build --target build` on a runner of its own architecture, `ubuntu-24.04` for x86_64 and `ubuntu-24.04-arm` for aarch64, and copies `/mneme` out of that stage. The build stage now targets `$(uname -m)-unknown-linux-musl`, where it named x86_64, and leaves the binary at `/mneme`, which the image copies too. Both base digests were already OCI image indexes with `linux/amd64` and `linux/arm64`, read with `crane manifest`, so no pin changed.
- **Each binary is checked** as `scripts/image.sh` checks the image's: it names no program interpreter, so it is fully static. It must also be an ELF for its own machine, and its `--version` must say the tag's version, so a tag that does not match `Cargo.toml` publishes nothing. The brief asked only that it runs. The job installs podman and readelf only when the runner lacks them.
- **Only the publish job may write,** with `contents: write` for the release and `id-token: write` to sign. It takes cosign from mise as `release.yml` does, without mise's cache, signs each binary with `cosign sign-blob --bundle` into `mneme-ARCH-linux.sigstore.json`, writes `SHA256SUMS`, and runs `gh release create --verify-tag`, which refuses a tag that is not on GitHub. The identity in each certificate is `https://github.com/notes-supply/mneme/.github/workflows/binaries.yml@refs/tags/vX.Y.Z`, which the `cosign verify-blob` of [install.md](install.md#verify-a-download) names. The bundle is cosign 3's default format; the classic format that `release.yml` uses is for Flux, which does not read these.
- **A version tags the image it was built from, and `latest` follows the newest version in a job of its own.** After the release, the `image` job, with `packages: write` and `contents: read` alone, finds `ghcr.io/notes-supply/mneme:<commit>`, which CI's release job pushed, and tags its digest `X.Y.Z` with `crane` from mise. It has no concurrency group, since a group keeps one pending run and cancels the others, which would skip a release's version tag. It fails and says so when the commit has no image, which happens when another commit reached `main` before its release job ran. The `latest` job then lists the `vX.Y.Z` tags newest first and tags `latest` on the image of the first that has one. It used to move `latest` in the same job when its own tag was the newest, but an older run that read the tags before a newer one was pushed could then move `latest` back after the newer run had set it. Every run of the new job gives the same answer, so its group, `image-latest`, can run one at a time and cancel a waiting run without losing anything. The signature is on the digest, so a new tag needs none. A server can then pin `ghcr.io/notes-supply/mneme:0.2.0` instead of a commit.
- **Not run yet.** The workflow runs only on a pushed tag. actionlint and zizmor, its pedantic persona too, find nothing. The x86_64 build stage is the one `mise run image` builds; the aarch64 one has not been built, since the build machine has no arm64 emulation.
